# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	ch := make(chan int) // небуферизований канал

	wg.Add(1)
	go func() {
		// симуляція важкої роботи
		ch <- 42
		wg.Done()
	}()

	wg.Wait()
	fmt.Println(<-ch)
}
```

## Мій промпт до ШІ

Вставте нижче точний текст промпту, який ви розробили. Промпт має
явно вимагати від ШІ:

- **не просто переписати код**, а пояснити точну послідовність
  переплетення (interleaving) горутин, що веде до зависання;
- проаналізувати, чому виклик `wg.Wait()` перед читанням з
  небуферизованого каналу зупиняє виконання.


### Мій промпт

Поясни, де саме виникає дедлок у цьому фрагменті Go. Розкрий
послідовність виконання горутин, яка призводить до зависання:

1. яка операція блокується першою і чому;
2. чому `wg.Wait()` не дає можливості продовжити виконання;
3. чому небуферизований канал тут є ключовим фактором;
4. якій взаємодії між `send` і `receive` не відбувається в правильному
   порядку.

Потрібно не просто переписати код, а саме пояснити точний порядок
переплетення (interleaving) горутин і показати, чому цикл очікування
`горутина -> wait -> канал -> горатина` ніколи не розривається.

## Пояснення від ШІ

Вставте нижче відповідь ШІ-асистента на ваш промпт — покрокове
пояснення переплетення горутин.

### Відповідь ШІ

Дедлок виникає через неправильний порядок виконання між двома
сценаріями: відправкою в канал і очікуванням завершення горутини.

1. У `main` створюється небуферизований канал `ch` і `WaitGroup`.
2. Після `wg.Add(1)` запускається горутина.
3. У цій горутині виконується `ch <- 42`.
4. Для небуферизованого каналу `send` блокується, поки інша goroutine
   не почне `receive` з цього каналу. Тобто горутина не може завершити
   виконання, доки хтось не прочитає `42`.
5. Після запуску горутини `main` викликає `wg.Wait()`. Це означає: "чекати,
   доки горутина завершить роботу".
6. Але горутина не може завершити роботу, бо вона зависла на `ch <- 42`.
7. В той же час ніхто в `main` ще не читає з `ch`, бо читання стоїть після
   `wg.Wait()`.

Тобто відбувається цикл:

- горутина блокується на `send`, бо ніхто не читає;
- `main` блокується на `Wait()`, бо чекає завершення горутини;
- жодна зі сторін не може зробити наступний крок.

Саме тут важливий небуферизований канал: він не накопичує значення,
а вимагає одночасної зустрічі `send` і `receive`. Якщо `receive` не
здійснений до того, як `send` намагається відправити, відправник
зупиняється. А оскільки `wg.Wait()` стоїть перед `receive`, ця
взаємодія ніколи не відбудеться.

## Мінімальне виправлення

Робочу, тестовану версію виправлення реалізовано в
[`deadlock/fixed.go`](./deadlock/fixed.go) (функція `Run`), а
автоматична перевірка — у `deadlock/fixed_test.go`. Коротко опишіть
своїми словами, яку зміну порядку операцій (чи структури каналу) ви
застосували і чому саме вона усуває циклічне очікування.

Я прибрала залежність від `WaitGroup` для цього простого сценарію і
зробила так, щоб горутина відправляла `42` у канал, а основна goroutine
читала його напряму в `return <-ch`. Важливо, що читання відбувається
перед будь-яким очікуванням завершення горутини, тому `send` і `receive`
взаємодіють через небуферизований канал у правильному порядку і не
утворюють циклу очікування. Через це дедлок зникає, а функція повертає
значення `42` без блокування.
